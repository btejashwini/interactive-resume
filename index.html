Technical Expertise

Technical explorations

How I reason about the systems behind enterprise products: the constraints, the options and the product questions they raise. Open a topic for the detail.

CRM architecture Data models, sharing, automation layers

What it covers

The object model behind sales and service processes (accounts, contacts, opportunities, line items, cases), who can see and change which records, and where automation lives.

How I approach it

  • Decide which system is the source of truth for each entity before designing screens or automation.
  • Layer automation deliberately: validation rules, then Flows, then Apex triggers through a single handler per object.
  • Design security models and data visibility up front. Sharing rules are hard to retrofit.

Product questions I ask

  • What decisions does this data need to support, and who makes them?
  • What reporting will leadership expect on day one?
  • How will data volume grow, and what breaks first when it does?
REST APIs and integrations Contracts, versioning, authentication

What it covers

REST and SOAP endpoint design, request and response contracts, versioning, and connecting Salesforce to ERP, billing and third-party platforms.

How I approach it

  • Agree the contract first: fields, formats, error shapes and versioning policy.
  • Keep credentials out of code with Named Credentials and OAuth 2.0 flows, and grant least-privilege permissions.
  • Choose synchronous calls only when the user is waiting for the answer. Otherwise go asynchronous (Queueable Apex, Platform Events).

Product questions I ask

  • What does the user see while the other system is slow or down?
  • Who owns the contract when either side needs to change it?
Salesforce-to-ERP integrations Bidirectional sync, mapping, reconciliation

What it covers

Keeping customer, order and billing data consistent between a CRM and an ERP that each own part of the picture.

How I approach it

  • Assign an owning system per field, not per object, and document the direction of sync.
  • Map fields explicitly, including picklist values and currency and date formats.
  • Prefer delta sync over full loads, make writes idempotent, and run periodic reconciliation to catch drift.
  • Define conflict resolution rules before go-live, not after the first conflict.

Case study in development. API failure handling Retries, backoff, monitoring and replay

What it covers

What happens when an integration call fails, and how the business finds out and recovers.

How I approach it

  • Separate transient failures (timeouts, rate limits), which are retried with exponential backoff, from data errors, which are not retried.
  • Route failures that exhaust their retries to a dead-letter queue or error log that people can see and replay.
  • Use idempotency keys so a retry can never create duplicate records.
  • Monitor and alert on failure rates, not just individual errors.

Product questions I ask

  • Who is responsible for clearing the error queue, and how quickly?
  • Which failures does a business user need to see, and which are purely technical?

Automation and scalability Governor limits, bulkification, async processing

What it covers

Making automation work at enterprise data volumes on a multi-tenant platform with hard limits.

How I approach it

  • Bulkify everything. Code must behave the same for 1 record or 200.
  • Choose the right asynchronous tool: Batch Apex for large volumes, Queueable for chained work, Platform Events for decoupled, event-driven flows.
  • Plan platform capacity and governor limits as product constraints, not afterthoughts.
